# 運用手順（人間向け）

## ローカルで確認する

外部パッケージのインストールは不要です（Node.js 22 以上だけ必要）。

```bash
node scripts/test.mjs             # 自己テスト（ネット接続なし。悪意ある入力を落とせるかも確認）
node scripts/validate-data.mjs    # データ検査
node scripts/build.mjs --offline  # ネット接続なしで _site/ を作る（自動取得の分野は「未取得」）
node scripts/serve.mjs            # http://127.0.0.1:8080/ で確認（自分のPCからのみ接続可）
```

本番と同じ取得を試す場合は `node scripts/build.mjs`（WHO・CISA に接続します）。

## コミット前の自動検査（任意・おすすめ）

```bash
git config core.hooksPath .githooks
```

以後、コミットのたびに個人情報・秘密情報とデータ形式を検査し、問題があればコミットを止めます。

## 毎日の自動更新

- GitHub Actions が毎日 05:43 と 17:43（日本時間）に取得 → 検査 → 公開
- 失敗した日は公開されず、サイトは前回の内容のまま（画面下部と説明ページの日時が古いまま止まる）
- **注意**：公開リポジトリで60日間コミットが無いと、GitHub は定期実行を自動停止します。週次の候補の追加など、運用者が定期的に PR を取り込んでいれば止まりません。2か月近く何も取り込まないときだけ、手動データの見直し（`reviewedAt` の更新）などを1回入れてください

## 自動更新が失敗したとき

1. Actions タブで失敗したジョブのログを見る
2. よくある原因
   - `HTTP 4xx/5xx`：取得先の一時的な不具合。翌日の実行を待つか、手動で再実行
   - `unexpected response shape`：取得先の形式変更。`scripts/fetch-*.mjs` の修正が必要
   - `too few items`：取得件数が異常に少ない。取得先の不具合の可能性。データを確認してから対処
   - 検査エラー：取得データに想定外の内容（HTML・不正URLなど）。安全側で止まっている状態なので、無理に通さない
3. 原因が分からない場合は、無理に直さずサイトを前回の内容のまま置いておく（それが安全な状態です）

## 手動データ（研究と対策・こころ・福祉）の追加

変更するのは `data/curated/entries.json` と `data/curated/changelog.json` の2ファイルだけ。国・分野別の公式リンク集 `data/directory/links.json` は運用者だけが更新する（URLは `scripts/allowed-sources.json` の `directoryHosts` に載っている機関のものだけ。ひらがな欄 `jaKana` に漢字が残っていると CI が止める）。手順の詳細は `ops/CURATION.md`、監査は `ops/AUDITS.md`。

1. AI 運用者または自分が作業ブランチで2ファイルを編集し、PR を作る
2. 監査担当（ops/ROLES.md）のレビューコメントを確認したうえで、運用者がレビューする。最低限ここを見る
   - 原典の URL を **自分で開き**、要約が原典と一致しているか
   - 原典が査読論文・公的機関・国際機関のどれかか
   - 断定・誇大・優劣の表現が無いか
   - 福祉は「〇〇によれば」の形になっているか
   - こころの分野に手段・方法の記述が無いか
   - PR の「不審な記述の報告」欄
3. 検査（validate）が通っていることを確認してマージ → 自動で公開

## エラーの知らせを受け取る（メール）

- GitHub の Settings → Notifications →「Actions」で、**失敗したワークフローだけをメールで知らせる**（Only notify for failed workflows）を選ぶ。届くのは GitHub アカウントに登録したメールアドレス（Settings → Emails）。公開してよいアドレスでなくても、外には見えない
- 知らせが来るもの：毎日の公開（Build and deploy）の失敗、週1回のリンクの検査（Link safety check）の「危険」「要確認」、PR の検査の失敗、CodeQL の失敗
- **注意：公開リポジトリでは、Actions の実行ログはだれでも見られる**。このサイトのプログラムは秘密情報を持たず、ログには取得元の名前・件数・検査の結果（ファイル名・項目の id・リンクの URL）だけを出す。秘密情報やセキュリティの穴の詳しい内容をログ・Issue・PR に書かない
- セキュリティの穴に気づいたとき（自分で・人から）：公開の Issue ではなく、Settings → Security → **Private vulnerability reporting**（非公開の報告）で扱う。直すまで内容を公開しない

## 確認・改装中の表示にする（緊急時）

- `ops/MAINTENANCE`（中身は空でよい）を main に置く PR を取り込むと、次の公開からトップ（地球儀）が「ただいま確認・改装中です」の表示になる。福祉の相談先・セキュリティ対策・このサイトについてのページはそのまま見られる
- 戻すときは `ops/MAINTENANCE` を消す PR を取り込む
- すぐに切り替えたいときは、取り込んだあとに Actions →「Build and deploy」→「Run workflow」で公開を1回動かす
- 存在しないページには「ページが見つかりません」（`404.html`）が出る。地球儀のデータが読めないときは、画面に「ただいま確認中です」と、見られるページの案内が出る

## リンク先の監視

- 週1回（月曜）、`link-check.yml` が、表示しているすべてのリンク（リンク集・都道府県・手動掲載の原典・動物の原典・説明ページ）を開いて調べる。「危険」「要確認」があると失敗し、メールで知らせが来る
- **自動で消す仕組みは、今は入れていない**。自動で消すには、(1) 公開の処理にリポジトリへの書き込み権限を持たせる（このサイトの安全設計に反する）か、(2) 検査の結果を GitHub の「成果物（artifact）」として残し、公開の処理がそれを読んで危険なリンクを表示から外す仕組みが要る。(2) は書き込み権限なしでできるが、新しい公式の Action（upload-artifact など）をコミットの SHA で固定して使う必要があり、運用者の承認のうえで別の版で入れる
- それまでは、知らせが来たら、運用者が該当のリンクを確かめ、危険なら evidence.json の記録を外す（表示されなくなる）PR を取り込む

## AI 専用の GitHub アカウント（マシンアカウント）は必要か

- **今の運用（AI は GitHub に一切書き込まず、運用者が自分でブラウザから取り込む）なら、必須ではない**
- 必要になるのは、AI や bot に、作業ブランチへの push や PR の作成を**自動で**させたくなったとき。そのときは、運用者のアカウントを AI に使わせず、AI 専用のアカウントを作り、このリポジトリへの権限を「読み取り＋フォークからの PR」にする（GITHUB-SETTINGS.md 6.1）。作るときは、作り方と接続のしかたを別に案内する

## 将来の多言語化

- 画面の文言は `site/i18n/ja.json`。言語を足すときは `en.json` などを追加し、`site/js/i18n.js` の `loadLanguage()` に切り替え UI をつなぐ
- データ側は `title` などが `{ "ja": "...", "en": "..." }` の形なので、言語別の文言を足せばよい
